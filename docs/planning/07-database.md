# 07. 데이터베이스 선택

- 상태: [결정] 관계형 DB, PostgreSQL 사용 (2026-11-11)
- 관련 문서: 03 (기술 스택, 데이터 모델), 06 (인증)

## 1. 결론

- 관계형 데이터베이스를 쓴다.
- 그중 PostgreSQL을 쓴다.
- 로컬 개발과 배포 환경을 같은 종류의 DB로 맞춘다.

## 2. 왜 관계형 DB인가

| 이유 | 설명 |
|---|---|
| 데이터 사이의 관계가 명확함 | 사용자, 구독, 크리에이터, 방, 메시지가 서로 연결되어 있음. 이런 연결은 외래키와 조인으로 관리하는 것이 자연스러움 |
| 정합성이 중요함 | 구독 상태, 역할 변경, 결제 결과는 중간에 어긋나면 안 됨. 트랜잭션으로 함께 저장하거나 함께 취소할 수 있어야 함 |
| 인증 라이브러리와 맞음 | Better Auth가 사용자, 세션, 계정 테이블을 관계형 구조로 만듦 |
| 팀 규모에 맞음 | 2명 팀이 한 DB를 단순하게 운영하기 좋음 |

### 검토한 대안

| 대안 | 장점 | 이 프로젝트에서 빠진 이유 |
|---|---|---|
| 문서형 DB (예: MongoDB) | 구조를 자유롭게 바꾸기 쉬움 | 구독과 결제처럼 관계와 정합성이 중요한 데이터에는 직접 관리할 부분이 많아짐 |
| SQLite | 설치가 필요 없고 파일 하나로 동작 | 여러 사용자가 동시에 쓰는 배포 환경에 맞지 않음. 로컬 연습용으로만 적합 |

## 3. 왜 PostgreSQL인가

| 기준 | 판단 | 근거 |
|---|---|---|
| JSON 데이터 | 강점 | 크리에이터 페르소나(`creator_profiles.persona`)와 메시지 본문(`messages.body`)처럼 형태가 자주 바뀌는 데이터를 JSONB로 저장하고 인덱스를 걸어 검색할 수 있음 |
| 확장 기능 | 강점 | 나중에 AI 반응 미리보기에서 유사 문장을 찾을 때 pgvector 같은 확장을 붙일 수 있음 |
| 배포 환경 | 맞음 | Render가 관리형 데이터베이스 서비스를 제공함 (아래 근거 1) |
| 인증 라이브러리 | 지원됨 | Better Auth가 PostgreSQL을 지원하며, 로컬에서 마이그레이션이 성공함 (아래 근거 2) |
| 비용 | 확인 필요 | 로컬은 무료. Render 무료 DB의 기간과 제한은 아직 확인하지 않음 |

### 검토한 대안 (관계형 안에서)

| 대안 | 장점 | 이 프로젝트에서 빠진 이유 |
|---|---|---|
| MySQL / MariaDB | 웹에서 널리 쓰이고 설정이 간단함 | JSON 검색과 확장 기능이 PostgreSQL보다 약함. 기능상 동작은 가능하지만 우선순위에서 밀림 |
| SQLite | 설치가 필요 없음 | 배포와 동시 접속에 부적합 |
| Supabase (관리형 PostgreSQL) | 인증과 DB를 함께 제공 | 인증은 Better Auth로 정했으므로 Supabase를 쓸 이유가 약함. DB만 필요하면 Render로 충분함 |

## 4. 근거

1. [사실] Render는 백엔드 서버, 데이터베이스, 실시간 기능을 함께 운영하는 클라우드 플랫폼이라고 공모전 페이지에 소개되어 있음. 출처: 프로젝트 문서 '공모전 홈페이지'의 Render 소개 항목
2. [사실] 로컬 PostgreSQL 16에서 `npm run auth:migrate`로 Better Auth 테이블 생성을 확인함 (2026-11-10, 로컬 테스트)
3. [사실] 이후 팀은 로컬 DB 대신 Render 공유 PostgreSQL(`cmms-db-01`, Singapore, 16.15)을 함께 씀. 마이그레이션 `0001`~`0006` 적용 확인 (2026-11-12). `0005`는 시참(팀원) 것

## 5. 알려진 한계와 대응

| 한계 | 대응 |
|---|---|
| 메시지가 많아지면 한 테이블이 커짐 | 메시지 테이블에 방(room)과 생성 시각 기준 인덱스를 두고, 필요하면 오래된 메시지를 별도 보관 |
| 실시간 전송은 DB가 잘하는 일이 아님 | DB는 저장을 맡고, 실시간 전달은 03 문서 2절의 실시간 방식으로 처리 |
| 로컬과 배포 DB의 설정 차이 | `.env.local`과 Render 환경 변수로 주소만 바꾸고, 같은 마이그레이션 명령을 사용 |
| 공유 DB라 테스트 데이터가 섞임 | 테스트 계정은 `cmms-test-*@example.com` 형식으로 만들고, 정리 여부는 테스트 후 확인 |
| 공유 DB라 마이그레이션 번호가 겹칠 수 있음 | 새 번호를 쓰기 전에 이슈로 알리고 `bubble_migrations`를 확인함 (#25). 실제로 `0005`가 겹쳐 프로필 사진을 `0006`으로 바로잡음 |
| 프로필 사진을 DB(`bytea`)에 저장함 | 512KB 이하로 제한하고 사진만 따로 테이블(`creator_avatars`)에 둠. 사진이 많아지면 Render 디스크나 외부 저장소로 옮김 |
| 실시간 알림용 `LISTEN` 연결 | 서버 인스턴스마다 DB 연결 1개를 계속 잡음 (#19). 인스턴스가 늘면 Render DB 연결 수 한도를 확인 |

## 6. 재검토 조건

아래 중 하나라도 해당하면 이 결정을 다시 검토합니다.
- 팀원이 MySQL을 강하게 원하고, 그 이유가 개발 속도에 실제로 영향을 줄 때
- Render 무료 DB 조건이 배포 계획에 맞지 않을 때
- 메시지 저장량이 예상보다 훨씬 커서 DB를 분리해야 할 때
