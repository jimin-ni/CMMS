## 게임 (join method library)

게임군마다 입장 방식이 달라서, 입장 방식을 **라이브러리**로 설계한다. 게임이 늘면 방식도 는다.

| 게임 | 한 판 정원 | 세션 정원 | 입장 방식 | 필요 정보 |
|---|---|---|---|---|
| 오버와치 | 6 | - | 인게임 검색-초대 | 배틀태그 |
| PUBG | 4 | - | 인게임 검색-초대 | 인게임 이름 |
| 갓필더 | 8 | ~12 | reveal-string(코드/암호) | 없음 |
| 마인크라프트 | 유동 | - | reveal-string(코드/초대) | 유저네임 |
| (예) 좀보이드 | - | - | 플랫폼 친구 초대 | Steam 친구코드 |

초기 입장 방식 3종:

1. **reveal-string** — 승인 시 코드/암호 문자열 노출 (갓필더, 마인크라프트)
2. **인게임 검색-초대** — 스트리머가 팔로워의 인게임 이름/배틀태그로 검색해 초대 (PUBG, 오버와치)
3. **플랫폼 친구 초대** — Steam 친구코드로 친구 추가 후 초대 (좀보이드, 향후)

- 승인 후 노출(reveal) 규칙은 입장 방식별로 다르다.

## 팔로워 게임 정보 입력

- 특정 게임 **첫 참여** 시 팝업: username / playername / steamcode 입력
- 오래 비운 **복귀자**: "이 이름이 아직 맞나요?" 재확인 팝업
- (필요 시) 오입력 면책 동의: "이름을 잘못 적으면 책임지지 않습니다"
- 저장 단위는 **게임별 핸들**. 크리에이터(및 큐 조작자)에게만 보인다.

## 팔로워 기능

- 팔로우한 크리에이터의 **시참 열림 알림**
- **승인 완료 알림**
- **준비(on-deck)** 또는 **참가자**일 때 입장 정보 노출(코드 복사 버튼, 검색-초대 안내) — 게임별. 준비 단계에서 미리 받아 둠
- 대기열 **나가기**
- 대기(참가 후보) 명단에 추가될 때 **presence 재확인**
- 내 **대기 순번(숫자만)** 실시간 표시
- **다중 큐 허용**. 큐를 잡고(언제든 **나가기** 버튼으로 뺄 수 있음) 자기 차례에 미참여하면 **쿨다운** 패널티. 적용 여부는 스트리머가 방별로 선택
- **쿨다운 / 재참여 규칙**

## 스트리머 기능

- **전원 대기열로**(kick all). 단 **고정(lock)된 멤버는 제외**
- **멤버 고정(lock)**: 특정 참가자를 kick all에서 지키는 핀. 스트리머 본인·합방 파트너 등 고정 멤버용 (룸 freeze 아님). 합방은 별도 표시
- **모집 멈춤/재개** 토글 하나. 매 판 상태 전환을 강요하지 않음. 작은 방은 게임 중에도 열어 둘 수 있음
  - 크리에이터: 방을 닫지 않고 신규 신청만 멈추고/다시 받음
  - 팔로워: 모집중/멈춤 신호로 지금 신청 가능한지 판단
- **승인 방식 선택**: 선착순(FCFS) / 추첨(룰렛) — 방별로 다르게
- **입장 질문**: 정답 일치 게이트. 질문/정답 입력 두 칸(위아래). **정확히 일치**해야 입장. 선택, 방별 설정
- per-user 제어: 대기열로 보내기 / kick / ban / 비공개 메모
- per-room 설정: 정원
- **예약 시참**: 사전 신청 오픈 또는 당일 오픈
- **준비(on-deck) 단계**: 대기열과 참가자 사이의 중간 명단. 흐름은 **대기열 → 준비 → 참가자** 3단계. 다음 판에 들어올 사람이 준비 단계에서 미리 준비(디스코드 접속·게임 실행·코드 확인)하고, 입장 안내/코드가 이때 전달됨
- **비공개 메모**(뷰어에게 안 보임) — 명예훼손/프라이버시 고려 (참고: 한국 명예훼손법, 당근마켓 매너온도·리뷰 모델)
- 큐 조작 **위임 가능성**만 열어 둠. 지금은 명시적 manager 역할 없음

## 결정됨

- **대기 명단 공개 범위**: 본인 순번(숫자)만
- **기본 승인 방식**: FCFS, 방별 설정 가능
- **핸들 저장**: 게임별, 첫 참여 입력 + 장기 복귀 재확인
- **메모**: 비공개 (뷰어 비노출)
- 서버 권한 슬롯 처리, 게임 핸들 데이터: 업계 표준 방식 채택
- **실시간 전송(시참)**: 폴링 GET → SSE. 크롬 토스트/푸시는 나중. WebSocket 미사용 (미니게임은 별도 검토)
- **no-show 패널티**: 쿨다운. no-show = 신청 후(나가기 가능) 자기 차례에 미참여. 적용은 스트리머가 선택
- **입장 질문**(옛 수락 질문): 정확 텍스트 일치 게이트. 질문/정답 두 칸
- **멤버 고정(lock)**: kick all 보호용 핀. 룸 freeze가 아님
- **모집 제어**: 모집 멈춤/재개 토글 하나로 단순화 (4단계 세션 상태 폐기)
- **방 설정은 라이브 편집**: 셋업 단계로 분리하지 않음 (정답 유출 시 수정, freeze 등 라이브 제어 필요)
- **제거**: per-row flag, 수동 순서 조정, 구독자 우선 승인 모드, 최대 대기 인원

## 실시간 푸시 요구사항

두 종류가 있고, 소켓은 탭이 열려 있을 때만 작동하므로 해법이 다르다.

- **A. 페이지 내 동기화** (방에 들어와 있음): 대기 순번, 슬롯, 세션 상태, 승인 노출
- **B. 페이지 밖 알림** (페이지에 없음): "시참 열림", "승인됨" → 소켓만으론 안 됨, 알림 채널 필요

이벤트:

- 승인 → 한 명에게, 즉각적인 느낌 필요
- 순번/슬롯 → **그 방 큐에 있는 사람에게만** (approve/reject/leave 때만 변함)
- 세션 상태 → 방 전체
- presence 재확인 → 한 명 왕복
- 신규 신청 → 스트리머 + 큐 조작자

핵심: 전체 시청자(예: 2,980명)가 아니라 **큐에 있는 사람에게만** 순번을 보낸다.

전송 방식:

| 방식 | 적합 | 메모 |
|---|---|---|
| 폴링 GET | PoC·소형 방 | 지민 현재 임시안(5초). 인프라 0. 대형 방은 thundering herd |
| SSE | 페이지 내 동기화 | HTTP 단방향, Render 친화, WS보다 간단. client→server는 일반 POST |
| WebSocket | (지금 불필요) | 양방향 최저지연. Render 지원 확인 필요(이슈 #9). 향후 라이브챗/리액션용 |
| Web/모바일 푸시 | 페이지 밖 알림 | "시참 열림"은 이것만 도달. 서비스워커/FCM. 마지막 단계 |

**결정(2026-11-11)**: 시참 페이지는 **폴링 GET으로 시작 → SSE로 업그레이드**. 페이지 밖 알림(크롬 토스트/푸시)은 **나중**. 시참에는 **WebSocket 미사용** (미니게임은 WS 가능성 별도 검토).

순서: 이벤트/데이터 모양 확정 → 폴링 구현(지민 순서와 일치) → 시참 동기화 SSE 업그레이드 → 페이지 밖 푸시.

## DB 접근 · 읽기/쓰기 규칙 (#17, 2026-11-11 확정)

공통 인프라 측(Jimin)이 우리 제안 2건을 채택해 `docs/planning/04-roadmap-and-team.md`에 기록(`a6c53da`). 시참·미니게임 모두 이 규칙을 따른다.

- **ORM: Drizzle.** 직접 `pg` SQL 대신 Drizzle ORM. 타입 검사로 공유 DB 실수 방지, SQL에 가까워 이전 쉬움, pgvector로 AI 확장 대비, Prisma보다 가벼움.
- **DB 접근은 `repo` 계층에만** 둔다. 컴포넌트·액션·핸들러에서 직접 쿼리하지 않는다. (예: `src/lib/bubble/repo.ts`)
- **스키마 기준은 `db/migrations/000N_이름.sql`.** Drizzle 테이블 정의는 `src/lib/schema.ts`에 그에 맞춰 둔다.
- **Better Auth 테이블은 `npm run auth:migrate`가 계속 관리**하고, Drizzle에서는 **조회만** 한다 (마이그레이션 금지).
- **읽기/쓰기 3분할:**
  - 쓰기(참여 신청, 큐 나가기, 승인 등) → **Server Action**
  - 첫 화면 읽기 → **Server Component**
  - 실시간 읽기(순번·슬롯·세션 상태 동기화)와 AI 스트림 → **GET Route Handler** (폴링 → 동일 주소로 SSE 업그레이드)

근거: Server Action은 클라이언트당 순차 실행이라 폴링이 전송을 막고 POST 전용. Route Handler는 폴링→SSE 전환과 LLM 스트리밍·외부 연동에 맞음. 위 「실시간 푸시 요구사항」의 폴링→SSE 결정과 일치한다.

**시참 테이블 추가 규칙 — 공유 DB:** 새 마이그레이션 번호(`000N`)로 추가하되, 번호가 겹치지 않게 **추가 전에 Jimin에게 통보**(Jimin 요청, #17). Better Auth 테이블은 건드리지 않는다.

**폴링 엔드포인트 참고 형태 (Jimin, 버블 선례):** `GET /api/bubble/rooms/[roomId]/messages?since=<커서>` → 커서 이후 생성·삭제분 + 다음 커서 + 방 상태 반환. 같은 주소로 나중에 SSE 전환. 시참 실시간 읽기(순번·슬롯·세션 상태)도 이 커서 기반 모양을 따른다.

**미정:** 실시간 전달 방식(Socket.IO / SSE / 관리형 서비스)은 공통 인프라 측에서 아직 미정. Jimin이 이슈 #19(실시간 전달 방식 결정과 적용)에서 추적하고, 결정은 04 문서 결정 로그에 남긴다.

## 데이터 모델 (`0005_sicham.sql`, 2026-11-11)

이전 HTML 초안(공유 `rooms` 재사용 + `sicham_session` 1:1 확장)은 폐기. main에 공유 `rooms`가 없고, 버블이 `bubble_*` 자체 테이블을 쓰는 선례를 따른다.

규칙 (main 선례):

- 자체 테이블 PK는 `uuid default gen_random_uuid()`, 사용자 FK는 `text references "user"(id)`.
- 열거형은 `text` + `check (... in ...)`. Drizzle에서는 `text({ enum })`.
- 팔로워 확인 없음. 버블과 같이 구독·결제 전까지 누구나 참여 (`subscriptions` 미생성, #12).

테이블:

| 테이블 | 역할 | 키 |
|---|---|---|
| `sicham_games` | 게임 카탈로그. 게임은 계속 늘 수 있어 코드 상수가 아닌 테이블 (반응 목록과 다름) | `id` text 슬러그 |
| `sicham_game_handles` | 게임별 핸들. 크리에이터에게만 노출 | `(user_id, game_id)` |
| `sicham_sessions` | 시참 방 (방송 1회분 모집) | uuid |
| `sicham_members` | 3단계 명단. `status`로 queue / ready / party 구분 | uuid |
| `sicham_bans` | 크리에이터 범위 영속 차단 | `(creator_id, user_id)` |
| `sicham_notes` | 크리에이터 범위 비공개 메모 | `(creator_id, user_id)` |

결정:

- **대기 순번은 저장하지 않는다.** `queued_at` 순서로 계산. 오류가 보이면 다시 검토.
- **입장 질문 답은 멤버에 저장하지 않는다.** 정확 일치 게이트라 저장값이 항상 정답과 같다.
- **세션당 사용자 활성 행 1개.** `(session_id, user_id) where status in ('queue','ready','party')` 부분 유니크 인덱스. 나간·킥된 행은 기록으로 남고 재신청은 새 행.
- **정원은 party에만 적용.** ready(준비)는 0명부터 무제한. `party_size` 초과 검사는 쓰기 시 세션 행을 잠그고(`for update`) 앱에서 한다.
- 입장 코드(`join_code`)는 ready·party 상태인 본인에게만 응답에 포함.
- **크리에이터당 닫히지 않은 시참 방 1개** (버블 선례). 부분 유니크 인덱스.
- **테이블 이름은 기능 접두어 `sicham_`** (main 관례). 게임 카탈로그도 시참 소유.
- **전원 대기열로(kick all)는 대기열 맨 뒤로.** 대상의 `queued_at`을 새로 찍는다. FCFS에서 참가자가 순환된다. 고정(locked) 멤버는 제외.
- **하드코딩 값:** 글자 수 상한(제목 50, 핸들 100, 입장 질문 200, 정답 100, 입장 코드 200, 메모 500)은 SQL `check`에 고정값. 게임 표시 정보(장르, 섬네일 그라데이션, 이모지)는 테이블이 아닌 코드(`src/lib/sicham/mock.ts`)에 있다. 새 게임은 섬네일이 없을 수 있음 — 게임 추가가 드물고 AI로 추가할 예정이라 그대로 둔다.
